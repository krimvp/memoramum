# ADR-0016 — Log remote MCP clients in with OAuth 2.1, as a resource server

**Status:** accepted · **Context docs:** [04](../04-agent-interface.md), [06 §1](../06-audit-privacy-security.md), [07 §1](../07-operations.md)

## Decision

The streamable-HTTP MCP endpoint ([ADR-0015](0015-remote-mcp-streamable-http.md)) is an OAuth 2.0 **resource server** — never an authorization server. It publishes protected-resource metadata (RFC 9728) at `/.well-known/oauth-protected-resource/<resource path>` naming the deployment's authorization server and this endpoint's resource identifier, and answers an unauthenticated call with `401` + `WWW-Authenticate: Bearer resource_metadata="…"`. That challenge is the whole login instruction: a spec-compliant MCP client discovers the authorization server, registers, runs authorization-code + PKCE with the endpoint as its RFC 8707 `resource`, and returns with an access token — no client-side configuration beyond the endpoint URL. Presented tokens are verified **locally** as JWTs against the authorization server's JWKS: signature, `iss`, `aud` = the resource identifier, expiry, and any required scopes. Login, consent, user records, and client registration stay with the org's IdP.

Verified claims map onto the principal pair through the seam [ADR-0014](0014-bearer-token-rest-auth.md) isolated (credential → proven actor), in order: an explicit `memoramum_actor` claim when the IdP knows Memoramum principals; else the OAuth client id through an enrollment allowlist (`MEMORAMUM_OAUTH_CLIENT_AGENTS`, `client_id=agent:sage`) — a non-empty allowlist means an unlisted client is refused, not fallen back on; else the token's subject acting as itself. The subject, when it is not the client (a client-credentials token names itself), becomes a **proven** `on_behalf_of` — the delegation ADR-0014 could only accept as asserted — and an `X-Memoramum-On-Behalf-Of` header that disagrees with it is refused rather than silently overriding. The flow context stays asserted per request, exactly as before.

Static principal-bound tokens keep working beside OAuth at the same door — a configured token is matched first, anything else with the shape of a JWS is verified as an access token — so platform components and IdP-less deployments are unaffected, and both facades share one resolution path (the REST facade accepts the same access tokens; agents still reach memory only through MCP, [doc 04 §5](../04-agent-interface.md)). With neither configured, the loopback-only dev-mode shim is unchanged.

## Alternative(s) considered

- **Static bearer tokens only** (the [ADR-0014](0014-bearer-token-rest-auth.md) status quo): nothing new to operate; but a human connecting a harness must be issued a long-lived secret out of band and paste it into a client, the credential never expires or revokes without a config change and restart, and delegation stays asserted. That is precisely the cost ADR-0014 wrote down and pointed at an IdP to retire.
- **Memoramum as its own authorization server** (the MCP SDK supports it): one component, works with no IdP; but it means owning login, consent, client registration, and a second identity store — and re-deciding who `user:dana` *is*, when every identity in this design comes from the surfaces and the org directory. It would make the memory service an identity provider by accident.
- **A bespoke login: session cookies, or an API-key-exchange endpoint**: simple to build; but MCP clients implement the OAuth flow and nothing else, so a homegrown protocol means per-client custom support — and a hand-rolled auth protocol in a service whose whole claim is a trustworthy audit trail.
- **Token introspection (RFC 7662) instead of local JWT verification**: revocation takes effect immediately; but it puts a synchronous call to the IdP in front of every tool call, and an IdP outage becomes a memory outage — for a design that would rather degrade to memoryless than stall ([doc 07 §5](../07-operations.md)). Short token lifetimes buy most of the revocation benefit without the coupling.

## Why OAuth 2.1 as a resource server wins here

1. **The audit invariant gets stronger, not just preserved.** Reads are events naming their actor ([ADR-0006](0006-log-reads.md)); OAuth proves the actor *and* — for a user-authorized token — the `on_behalf_of` that everything else in the design can only take on trust. The [doc 05 §4.1](../05-policy.md) intersection rule now fences a proven claim.
2. **It is the login MCP clients already know how to do.** Discovery + challenge means a harness needs the endpoint URL and nothing else — no secret to distribute, so the credential distribution problem that pushed ADR-0015 toward central deployment does not come back at the agent's side.
3. **Identity stays where identity lives.** Joiners, leavers, MFA, and revocation are the IdP's job; Memoramum keeps deciding only what a principal may *see* (ReBAC + policy, [doc 05](../05-policy.md)). No second user store to drift.
4. **It reuses the seam rather than adding an enforcement point.** The API core, policy evaluation, and event log are untouched: one resolver learned a second credential kind. Two facades, one issuance story.
5. **Expiry and rotation arrive for free**, retiring the static-token cost for interactive callers while leaving static tokens available for the machine callers where they fit.

## Costs accepted

The interactive path now depends on an authorization server being reachable: JWKS discovery failure is an explicit `503`, never a quietly open door, and deployments without an IdP keep static tokens. Local verification means a revoked token stays usable until it expires — bounded by the IdP's lifetime setting, an accepted trade against introspection's per-call coupling. Two credential kinds meet at one door — configured tokens matched first, JWS shape deciding the rest: a small permanent branch, and the reason both must resolve to the same `VerifiedCredential`. The flow context remains asserted rather than proven ([ADR-0015](0015-remote-mcp-streamable-http.md) costs). And where an IdP allows dynamic client registration, any client a user consents to can obtain a token: with `MEMORAMUM_OAUTH_CLIENT_AGENTS` configured, an unenrolled client is refused; without it, such a client acts *as that user* — never beyond what the user could see, which is the same bound the intersection rule places on every delegated call. Deployments that care about which agent is speaking should enroll clients, and may require a scope the IdP grants only to approved ones.
