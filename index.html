Design overview

Memoramum

A standalone memory service for AI agents — a Slack assistant, an MR-review bot, tomorrow's surfaces — that lets them learn, remember, and forget under explicit policy, with every memory auditable from the moment it was proposed to the moment it was erased.

This page is the two-minute version. The normative design lives in the README and docs 01–07.

The bet

Agents without memory re-ask everything. Agents with naive memory are worse: they hoard stale facts, leak across contexts, and can be poisoned by anything they read. Existing systems (Letta, Mem0, Zep, LangMem) each solve pieces; none treats provenance, scoped access control, and governance as the core. Memoramum does:

🔍 Auditable by construction

Every memory knows its source messages, its actor, and its justification. Every write and every read into an agent's context is an event in an append-only log — "why did the bot say that?" is a query, not forensics.

🎯 Scoped by default

A memory learned in a channel belongs to that channel. Wider visibility is an explicit, policied, audited promotion — never a side effect.

⚖️ Governed by policy

A layered policy engine decides what each agent may learn, where it routes, what it may read, and what needs a human. Default deny: no policy, no learning.

🍂 Forgetting is a feature

Memories decay out of retrieval, get superseded on contradiction, expire on TTL, and can be hard-erased GDPR-style — leaving a content-free tombstone in the audit trail.

Design choices behind the shape: it is a standalone service so policy and audit are unbypassable — no agent embeds the storage layer (ADR-0005). Agents speak MCP (six tools: memory_recall, memory_remember, memory_reinforce, memory_forget, memory_promote, memory_status); platform code uses REST. Everything lives in one Postgres (+pgvector) so a memory, its provenance, its policy decision, and its audit event commit in a single transaction (ADR-0004). Background workers — extraction, the consolidator, sweeps — produce memory quality offline so the hot path stays fast.

Core concepts

Memories

The atomic unit: one short natural-language claim ("Team Atlas deploys to production only on Tuesdays") with exactly one kind, one scope, one lifecycle status, and full provenance back to verbatim episodes (the exact Slack message or MR comment it came from). Content is immutable — corrections create a successor and close the predecessor's validity window.

semantic

Facts, preferences, constraints. Superseded on contradiction.

episodic

What happened; lessons kept as exemplars. Decays fastest.

procedural

How the agent should behave. Highest-risk kind — writes usually require a human.

profile

Bounded per-subject document (timezone, preferences). The one update-in-place exception.

Scopes — who can see what

Every memory lives in exactly one scope; scopes form a tree plus two parallel families:

org:acme
├── surface:slack
│   └── workspace/T024B ── channel/C0DEP ── thread/…     (container scopes)
├── surface:gitlab
│   └── project/platform-api ── mr/482
├── subject:user/dana        (about a person, cross-surface — the GDPR family)
└── agent:sage               (an agent's private notebook)

A read resolves a scope chain — thread → channel → workspace → org, plus the subject scopes of participants and the agent's own scope — computed server-side from the agent's declared context; agents can't ask for arbitrary scopes. The source-visibility invariant (Slack's contract, adopted wholesale): a memory never surfaces to someone who couldn't see its source episodes, checked at retrieval time. Cross-surface sharing isn't a mechanism of its own — it's just placement in a scope both surfaces can read, reached by promotion.

How a write works

candidate memory→ classify
categories · sensitivity · PII scan→ policy layers
org → surface → agent → user-pref→ verdict→ store + POLICY_DECISION event

Every write resolves to one of four verdicts, layers composing strictest-wins (an agent-level allow can never beat an org-level ask):

allow — written active stage — usable but quarantined ask — a human confirms first deny — refused, still logged

The default is staged: agent-inferred memories are immediately useful but rank-penalized, visibly fenced in context blocks, and unable to overwrite trusted memories. They earn active through reinforcement — independent re-observation, useful retrievals, or explicit confirmation. Only an explicit user "remember this" skips staging. This is also the poisoning defense: injected "memories" die at the policy gate or sit quarantined until corroborated by independent evidence.

Life of a memory

staged— reinforcement → active— pin → invariant
active— contradiction → deprecated— decay / TTL → archived— erasure → tombstoned

Two clocks run independently: lifecycle status (the system's operational stance) and bi-temporal validity — when a fact was true in the world (valid_at/invalid_at) versus when the system learned it (recorded_at). Contradictions never edit or delete: they close the old memory's validity window and link a successor, so "what did we believe in April?" and "when did the deploy policy change?" both stay answerable.

Forgetting is retrieval-side first: an Ebbinghaus retention curve R = exp(−t/S) multiplies into every retrieval score, so unused memories fade before anything touches rows. Reinforcement bumps strength S; frequently useful memories become effectively permanent. Hard paths — user "forget that", provenance-based quarantine, TTL, GDPR erasure — physically delete content and embeddings and leave a content-free tombstone event.

How agents read

PathWho initiatesWhat it does
Ambient recallPlatform, at session/turn start Service assembles a bounded context block for the scope chain: invariants first, then active facts, then a clearly-fenced [staged] section — every line with a provenance hint.
Deliberate recallThe agent, mid-task memory_recall with a natural-language query — hybrid vector + lexical retrieval, scored by relevance × retention × trust × status × scope proximity.

Access control runs before scoring (never post-filtering), and every delivery emits a READ event listing the memories that entered context (ADR-0006) — the one log most systems skip, and the only way to answer "why did the bot say that?".

The worked scenario

One story threads through every doc — Sage (Slack agent), Marge (MR-review agent), and dana:

  1. Learn. Sage observes dana in #deploys: "Team Atlas deploys to production only on Tuesdays." Policy says stage → stored scoped to that channel, provenance pointing at dana's exact message.
  2. Reinforce. Re-observed two weeks later and retrieved usefully → the consolidator promotes it to active.
  3. Promote. dana asks Sage to share it with the other teams. Channel → workspace crosses into a shared scope → ask → dana confirms → audited promotion.
  4. Cross-surface recall. Marge, reviewing an MR that schedules a Friday deploy, resolves her scope chain (repo → org + shared scopes), retrieves the memory, and flags the conflict.
  5. Forget. Months later: "we've moved to daily deploys." Contradiction closes the old memory's validity window, links a successor; the old fact stops surfacing but stays queryable as history.
  6. Audit. "Why did Marge warn about Tuesdays on MR !482?" — the READ event, the memory, its promotion, its reinforcements, and dana's original message are one traversal away.

Where the ideas come from

Deliberately assembled from proven pieces: bi-temporal supersession from Zep/Graphiti, background "sleep-time" consolidation from Letta, extraction pipelines from Mem0, the memory-kind taxonomy from LangMem/CoALA, retrieval-time access checks from Slack AI, layered allow/ask/deny policy from Claude Code. The novel part is the combination: provenance, scoped access, and governance as the spine rather than bolt-ons. See the prior-art appendix and the six ADRs for the contested calls.
